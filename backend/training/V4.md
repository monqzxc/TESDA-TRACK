# Train Kapampangan and Ilocano in Google Colab

Use [train_colab_v4.ipynb](colab/train_colab_v4.ipynb) to fine-tune TESDA-TRACK's existing
qualification matcher for **Kapampangan, Ilocano, English, Filipino, Cebuano and Hiligaynon**.
Taglish examples are retained. Training starts from `intfloat/multilingual-e5-small` and
exports the 384-dimensional ONNX model used by the app.

**Status:** a first full run (`scenarios-20261020-03`) is trained, measured and published at
[huggingface.co/Nyanta19/tesda-e5-small-v4](https://huggingface.co/Nyanta19/tesda-e5-small-v4); its model card
holds the dev, sealed and v1-test comparison against v3. It ties v3 on dev top-1 and rejects more unrelated
goals, so v3 remains the recommended serving model for now. Regional examples are synthetic drafts; fluent
speakers must check their grammar, meaning, spelling and qualification labels before relying on them.
This trains matching between career goals and qualifications, not a translation or chat model.

## 1. Start a Colab experiment

1. Open [Google Colab](https://colab.research.google.com/) and choose **File → Upload notebook**.
   Upload [train_colab_v4.ipynb](colab/train_colab_v4.ipynb).
2. Choose **Runtime → Change runtime type → T4 GPU**, or another available CUDA GPU.
3. Keep `SMOKE = True` and `USE_DRIVE = True`. Run the cells in order. Authorize your Drive
   mount when Colab asks, then upload `backend/training/runs/colab-bundle-v4.zip` when prompted.
4. The six-step smoke run checks training, ONNX export and vector parity. Its final cell
   prints instructions rather than downloading a smoke model.
5. After the smoke passes, set `SMOKE = False` and rerun from Settings. Keep the same `ROUND`
   for the matching full run; smoke and full outputs use different folders.
6. Download `tesda-e5-small-v4.zip`. A copy, trainable weights and resumable checkpoints
   remain under `MyDrive/tesda-track-training/` when Drive is enabled.

The notebook uses the project's pinned training libraries with Colab's installed PyTorch.
An actual GPU smoke run is still necessary to verify that combination in your runtime.
Colab's [GPU availability and runtime limits](https://research.google.com/colaboratory/faq.html)
vary. If memory runs out, change `MINI_BATCH` from 8 to 4 and choose a new `ROUND`, such as
`v4-small-batch`. An interrupted run can resume with the original bundle and settings.
When returning after a disconnect, rerun all cells; the notebook detects the saved checkpoint.

The bundle is cached in Drive. After revising data, replace that cached
`colab-bundle-v4.zip` with the rebuilt file and use a new `ROUND`. The notebook refuses
to mix a different bundle or settings with an old run. Without Drive, Colab runtime
deletion can lose both checkpoints and completed weights.

## 2. Review and expand the language data

[data/v4/regional_tasks.json](data/v4/regional_tasks.json) contains:

| Language | Task drafts | Other examples |
| --- | ---: | --- |
| Kapampangan (`pam`) | 334 | Two job-request patterns expanded across catalog jobs |
| Ilocano (`ilo`) | 344 | Existing job-request patterns |
| Cebuano/Bisaya (`ceb`) | 334 | Existing job-request patterns |
| Hiligaynon/Ilonggo (`hil`) | 334 | Existing job-request patterns |
| English / Filipino / Taglish | Retained from earlier datasets | Catalog, synthetic goals and Core-task examples |

The file retains the original 70 drafts and adds **1,276 workplace scenario queries**:
one new scenario for each of the **319 qualifications in the committed catalog**, expressed
in all four regional languages. Examples describe practical training needs: repairing a
delivery motorcycle that will not start, preparing hotel rooms, processing sea-import
documents, or building a booking website. These are synthetic learner requests for the
qualification matcher, not official assessment questions or observed learner conversations.

The scenarios use regional phrasing with English trade terms and are explicitly marked
`query_style: "code_switched_scenario"`. The loader's existing `native_task` kind includes
these mixed-language drafts; it does not mean they are fully native-language translations.
This gives catalog coverage, not broad conversational coverage or verified language quality.
All new rows remain `draft` pending fluent-speaker and TESDA subject review.

Each new scenario includes a stable `scenario_id`, exact `core_competencies` from its
catalog entry, and the entry's `source` (TESDA publisher, regulation download ID and list
URL). The [TESDA Training Regulations directory](https://www.tesda.gov.ph/Download/Training_Regulations)
is the official reference; the detailed competency mapping comes from this repository's
`seed/qualifications.json`. Coverage refers to that catalog snapshot, not a fresh national
registry import. New catalog qualifications need new scenario families. Review especially
the boundaries between related trades and NC levels; add other correct owners when needed.

Job patterns intentionally keep official English job titles. Repeating two patterns
over many jobs does not create broad language understanding. Counts in `by_language`
describe enrichment rows, not a balanced corpus or the entire training dataset.

Each task has `query`, `english`, `lang`, `qualification`, `kind` and `review_status`.
The English field is the **intended meaning**, also subject to review. English glosses,
review status, scenario IDs, competency references and source metadata are not model inputs.
Only the query and its catalog passage form a training pair. The four language variants of
a scenario share its ID and meaning; do not treat them as independent evaluation examples.

For review:

1. Have a fluent speaker correct each query against its intended English meaning and
   check that people would naturally say it. Include local spellings and code-switching.
2. Have a TESDA subject reviewer check the exact qualification label. An example may
   accept several qualifications; represent each correct owner as a separate training row.
3. Correct existing rows **in place**, then set `review_status` to `reviewed`. Keep a
   separate record of who reviewed the data; do not put personal details in the bundle.
4. Review Kapampangan's two generated patterns in [v4.py](v4.py) and the inherited
   Ilocano/Cebuano/Hiligaynon patterns in [v3.py](v3.py). Their expanded rows remain
   conservatively marked as drafts in the audit.
5. Add independently written goals involving tasks, informal phrasing and mixed languages.
   Each qualification currently has only one new scenario family. Expand the range of
   situations and usage styles, including informal problem descriptions, rather than just
   repeating request patterns. Language reliability depends on measured results, not row counts.

Copy [templates/regional_review.json](templates/regional_review.json) to a new filename
inside `data/v4/` to add new examples. Replace its sample queries and meanings. Use exact
qualification names from `seed/qualifications.json`; do not paste unlabelled text or
chatbot instruction datasets into this file. The loader validates labels, languages,
nonempty meanings and `draft`/`reviewed` status. Drafts are included for experimentation.

To extend to another regional language later, add its code/name and any reviewed job
patterns to `v4.LANGUAGES` / `v4.JOB_TEMPLATES`, register its code in `goals.LANGS`, and add
training and separate evaluation examples. No embedding dimension change is needed.

## 3. Rebuild after editing data

From the repository root in PowerShell:

```powershell
Set-Location backend
../.venv/Scripts/python.exe -m training.v4 --output training/runs/v4-coverage.json
../.venv/Scripts/python.exe -m training.bundle --output training/runs/colab-bundle-v4.zip
```

The bundle contains training code, catalog passages, draft examples and evaluation
exclusion hashes. It excludes credentials, learner records, trained weights and the
evaluation goal files. All earlier training exclusions still apply. The coverage audit
reports exact current row/pair counts and overlap; overlap must be zero.

Optional hard-negative mining uses `training.mine --profile v4`; supply the resulting
file to `training.bundle --hard-negatives PATH`, then set `HARD_NEGATIVES = True` and
`NEGATIVE_FILE` in the notebook. The default works without this step.

## 4. Measure the downloaded model before enabling it

Extract the serving ZIP into a new `backend/models/tesda-e5-small-v4/` folder. Run from `backend/`:

```powershell
# Score the base model on exactly the same expanded dev set.
../.venv/Scripts/python.exe -m training.evaluate --model intfloat/multilingual-e5-small --set dev --calibrate --min-rejection 0.9 --json training/runs/base-v4-dev.json
# Calibrate the new model on dev only.
../.venv/Scripts/python.exe -m training.evaluate --model-path models/tesda-e5-small-v4 --set dev --calibrate --min-rejection 0.9 --json training/runs/v4-dev.json
```

Also compare against your currently deployed model using its `--model-path`.
Inspect `metrics.dev.language_details`, its sample counts and the `errors` list.
Check English/Filipino regressions and rejection of unrelated goals as well as regional
top-1/top-3 performance. Compare models calibrated on dev under the same rejection target
before concluding one is better; both commands above use that same calibration procedure.

Kapampangan has **seven dev and five sealed synthetic regression examples**, including
unrelated goals. They are not a representative benchmark. Review and expand evaluation
data separately from training. Write fresh goals; keep translations/paraphrases of the
same underlying evaluation example out of training. Exact-text exclusion and grouped
loss splits cannot detect semantic leakage. Rebuild the bundle after changing evaluation
data so its exclusion hashes stay current. Keep the sealed set out of tuning.

After accepting dev results, save the dev-calibrated parameters (the check rejects
reports below the requested overall rejection floor):

```powershell
../.venv/Scripts/python.exe -c "import json; from pathlib import Path; r=json.loads(Path('training/runs/v4-dev.json').read_text()); assert r['model']=='tesda-track/tesda-e5-small-v4'; assert r['metrics']['dev']['rejection'] >= 0.9; Path('models/tesda-e5-small-v4/calibration.json').write_text(json.dumps(r['params'], indent=2))"
../.venv/Scripts/python.exe -m training.evaluate --model-path models/tesda-e5-small-v4 --set test_v1 --json training/runs/v4-test-v1.json
../.venv/Scripts/python.exe -m training.evaluate --model-path models/tesda-e5-small-v4 --set sealed --final --json training/runs/v4-final.json
```

Only use the sealed set once for a final candidate. ONNX parity and decreasing training
loss verify different things; neither establishes regional-language accuracy.

## 5. Connect the accepted model to TESDA-TRACK

Set these values in the repository-root `.env`, using your actual new model folder name:

```dotenv
SEMANTIC_SEARCH_ENABLED=true
EMBEDDING_MODEL=tesda-track/tesda-e5-small-v4
EMBEDDING_MODEL_PATH=backend/models/tesda-e5-small-v4
```

From `backend/`, run `../.venv/Scripts/python.exe -m tesda_track.embeddings sync`,
then restart the API. Re-embedding is required because the vectors changed. Test the
full API with your reviewed goals: its keyword and rejection rules can affect results
beyond the embedding model. See [model deployment](../models/README.md) for Docker paths.

The [E5 model card](https://huggingface.co/intfloat/multilingual-e5-small) describes its
`query:` / `passage:` prefixes and limitations. Existing training and serving code keep
these prefixes and the same passage format.
